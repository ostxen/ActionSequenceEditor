## 后续实施决策：原版优先与共用 JSON

2026-11-09 用户在体验后否定先前工作台的布局与完成度，要求先补原版可靠性，再用原生 UI Toolkit 尽量复刻原布局和操作。该决定覆盖本文早期“无需完善旧 UI”及 A01 的 `.asset` 正式入口取舍，历史分析不删除，但不再当作当前入口现状。

当前 `Open Action Editor` 与 `Open Workbench` 分别为 GUILayout 和原生 UI Toolkit，二者共用 `App.Session`、原有 Asset/Group/Track/Clip 和同一 FullSerializer JSON，不做旧新格式互转。共用服务负责原子保存、外部修改保护、Undo 快照和编辑命令。先前 ActionDocument `.asset` 工作台保留为实验，不自动转换或删除用户数据。Combat 仍暂缓，不因本轮 UI 完成而开始业务接入。

原生界面沿用顶部播放区、文档栏、标尺、轨道头、滚动时间轴、底部范围与独立 Inspector。几何检查、真实指针事件、保存重载和截图只提供证据，最终布局与操作验收由用户完成。自定义 IMGUI 业务 Header/Inspector、任意 Unity Object 引用持久化及逐像素显示差异必须单独说明，不能声称自动等价。进度和实际测试计数只维护在[唯一任务清单](../.codex/tasks/action-editor-refactor.md)。

## 2026-11-10 原版源码重构评估（建议，尚未开始结构迁移）

本节以本地提交 `6cd5483` 后的共用 JSON 实现为基线，回答“如何提高原版的扩展性、架构清晰性和可读性”。已实施放弃修改/关闭播放两项生命周期修复。2026-11-10 用户确认不同 UI 共用逻辑与数据，要求列出任务、准备逐一实施，并保留现有布局、交互操作方式及细节；具体拆分见[唯一任务清单](../.codex/tasks/action-editor-refactor.md)第4.1节。当前仅准备计划，结构迁移按后续指定任务执行，不自动推进 Combat。旧章节中的 `.asset` 方案不覆盖当前 JSON 入口决定。

### 一、判断：先归一行为所有权，不先换 UI 或拆目录

当前并非没有分层：已有 `JsonDocumentSession`、`ReliableFileCommit`、`JsonEditCommands`、分区 View 与自定义扩展 Attribute。问题是边界没有闭合：窗口仍负责事务收尾和播放退出，绘制器/菜单仍可直接写模型，两套 UI 又各自解释同一条业务规则。最近“放弃只改窗口标志”“关闭只重置预览”正是文档、视图、播放的所有权分散造成的。

| 源码事实与定位 | 结构问题 | 建议 |
|---|---|---|
| `Editor/App.cs` 同时包含打开/切换弹窗、会话恢复、自动保存、Unity Selection、播放状态与窗口重绘 | 静态全局上下文同时充当协调器、状态容器与 UI 服务 | 提取应用上下文及窄职责服务，App 暂作迁移外观；不把静态全局换成另一个巨型单例 |
| `JsonDocumentSession.cs` 同时负责 JSON、校验、文件导入、恢复及 Undo；`IsDirty` 每次重新序列化整图 | 存储边界与编辑事务耦合，脏检查成本随文档增长 | 分开编解码/存储与会话；命令覆盖完毕后再引入内容版本，保留保存基线比较 |
| `ActionEditorWindow.OnGUI` 按事件开启/结束事务；`ViewBase.CheckPointerEvent` 维护另一份手势状态；`ItemDragger` 静态缓存拖动对象 | 事务归属靠事件时序推断，取消入口难以穷尽 | 一次手势明确持有一个事务令牌，只有持有者可提交/取消 |
| `TimelineTrackItemView` 与 `JsonTimelineCanvas` 分别实现创建菜单、锁定、吸附和时间修改 | 共用 JSON 不等于共用编辑行为 | UI 只发命令，执行层统一检查挂载、唯一性、锁定、时间与重叠 |
| `EditorCustomFactory`、`CustomizedDrawTools`、`AssetPlayer.InitializePreviewPointers` 分别扫描类型 | 注册冲突、继承回退与缓存生命周期规则分散 | 一个类型目录解释元数据，显式处理精确注册、基类回退及冲突 |
| `InspectorsBase` 与 `JsonPropertyView` 分别反射字段、解释条件、创建集合元素 | 字段语义和事务写入重复，Toolkit 还反向引用 IMGUI 工具方法 | 共享字段描述/属性路径和编辑操作，不共享具体控件 |
| `IDirectable` 混合 Actor、折叠、锁定、时间、混合、序列化；`CanScale` 由 Length 声明类型推断 | 接口过宽、空 setter 和隐式能力增加阅读成本 | 先以 Editor 类型能力描述替代推断，不立即新增大量 Runtime 接口或改格式 |

这里列出的性能问题是调用路径事实，不是本轮实测瓶颈；任何优化预算需用最重真实文档另测，不能以“拆服务”宣称性能已经提升。

### 二、建议的最小职责结构

```text
Unity 窗口宿主
  ├─ IMGUI 视图适配器：GUILayout / Event.Use / 原版皮肤
  └─ Toolkit 视图适配器：VisualElement / Painter2D / PointerCapture
        ↓ 同一应用上下文（当前仍是一份共用文档）
  DocumentSession   内容、保存基线、Undo 与事务归属
  Editing          命令、选择、剪贴板及候选校验
  Timeline         可见行/命中几何、时间变换、手势与吸附
  Properties       字段描述、属性路径、条件及集合修改
  Playback/Preview 播放时钟与状态、预览求值及资源释放
        ↓
  DocumentCodec/Store：现有 JSON + 原子提交 + AssetDatabase 适配
  TypeCatalog：现有 Attribute 元数据 + 必要的可选扩展工厂
        ↓
  Runtime Asset / Group / Track / Clip（本轮不改格式）
```

这是一组职责，不要求一个职责一个程序集/接口。先在现有 Runtime/Editor 边界内整理；只有出现真实替换实现或测试隔离需求才抽接口。依赖由窗口组合入口显式传入，不引入 DI 容器、通用消息总线、完整 MVVM 或插件加载框架。

RF03已落地最小共享上下文：`ActionEditorContext`拥有会话、源资源、选择、剪贴板和播放状态，App及AssetPlayer.Inst只转发；两个真实窗口经幂等注册接受通知并转交更新资格。尚存的App.Window/Width、原版静态手势、Prefs/Styles和宿主恢复依赖明确保留，后续按任务迁移，不把此切片解释为全部规则已归一。真实双窗口顺序/重建/关闭、失败切换与无窗口服务测试及编译证据见唯一任务记录RF03。

RF04将活动编辑归属落到会话令牌：双UI、原版Inspector与拖动器只结束自己的令牌，环境式嵌套命令仍归外层；全局放弃/换图/撤销使旧令牌失效。Toolkit活动手势阻断错误按钮释放触发菜单，自身失焦仍取消。原版静态拖动器未在本切片改成每视图控制器，显式保存的活动事务策略、存储边界和完整桌面焦点链仍分别由后续任务及人工验收覆盖，不能把令牌理解为所有命令已隔离。

RF05把JSON编解码/比较移入JsonDocumentCodec，把路径、revision读写、ReliableFileCommit与Unity同步导入移入JsonDocumentStore；JsonDocumentSession只保留图、事务、Undo和基线/恢复。复用既有可靠提交，不改格式，不为单实现增加接口容器；旧静态入口作为兼容转发。Store先拒绝覆盖再构造保存快照，Session在导入前记录已提交基线。固定单目标持久探针覆盖占用、恢复、自动保存入口和外部保护；真实导入失败、系统对话框及完整域重载仍是明确缺口。

RF06已由DirectableTypeInfo缓存类型事实，ActionEditorTypeCatalog缓存现有发现及菜单描述，EditorCustomFactory按精确/明确允许的最近基类缓存解析并诊断无关冲突。未实例化预览或UI进行发现，不用类型描述存锁定状态。两UI属性邻居界限共用ClipTimingRules，保留与严格边缘拖动的原有差异；候选手势和预览工厂继续由RF09/RF12迁移。

**所有权规则：**

- 文档内容和保存基线归 DocumentSession；不通过窗口脏标志推断是否保存。
- 选择/剪贴板归会话级编辑上下文；视域、滚动、折叠、分栏归工作区。暂不删除已有序列化字段或重写样本，先隔离访问。
- 手势状态归当前视图的控制器；共享文档上只能有一个明确拥有者的活动编辑。关闭/失焦不得结束另一视图的事务。
- PlaybackController 唯一驱动时钟，PreviewSession 拥有预览对象及回调；窗口只发送播放/暂停/停止意图，宿主统一处理域重载与关闭策略。
- 提交、撤销、回退、选择和工作区变化使用有意义的通知；不能每次缩放都释放预览，也不能每次属性更改都全树重建。最终策略以实际依赖决定。

### 三、扩展性应体现为“新增业务不用改核心分支”

保留 `Name/Description/Category/Color/Attachable/Unique`、条件字段和 `ISubClipContainable`；由类型目录一次性解释成只读描述，不要求业务把同一份名称/分类再注册一遍。

类型描述只包含真实需要的内容：模型类型、节点种类、显示元数据、构造工厂、挂载/唯一性规则；Clip 增加点/区间、伸缩、渐入/渐出能力，附可选校验、Header/属性/预览工厂。锁定与停用是对象状态，不是类型能力。重叠是接收邻居和候选时间的校验策略，不简化成全局 AllowOverlap。

解析顺序为“精确匹配 → 明确允许的最近基类回退 → 默认实现”，重复精确注册报告双方来源。发现阶段不实例化窗口、不求值预览。现有 Attribute 可由适配层生成注册项；自定义 IMGUI Inspector 不自动转换为 Toolkit，缺少适配时明确提示能力边界。

实验 `EventRegistry` 的原子发布、工厂独立性检查和冲突诊断值得复用，但它绑定 `ActionDocument/TimelineEvent`，属性上下文还依赖 Toolkit，不能直接替换 JSON 类型目录；不借此引入新 TypeId、数据迁移或泛型万能注册框架。

### 四、分阶段迁移与验收建议

以下 RF0–RF5 是架构阶段名，非独立执行清单；对应的 RF01–RF15 实施任务、依赖、U01–U14交互矩阵及唯一状态记录在任务文档第4.1节。列出任务不代表已完成或获得自动全量实施授权。

| 顺序 | 最小迁移交付 | 必须满足的验收 |
|---|---|---|
| RF0 行为基线 | 固定原版体验、样例与双 UI 操作矩阵；将待确认缺陷转为失败测试 | 明确保持的行为与刻意修正的行为；候选问题不冒充运行复现 |
| RF1 上下文与生命周期 | 组合入口、实例上下文、明确事务令牌；收拢打开/保存/放弃/关闭/自动保存/时钟 | 双窗口切换、关闭顺序、失败恢复、域重载、重复取消不串状态；App 只留渐进转发 |
| RF2 类型目录与命令 | 集中解释元数据、工厂、挂载/唯一性及候选校验，两个 UI 调同一命令 | 新建/复制/粘贴/重排结果一致；锁定/冲突失败无部分修改，一次提交一次 Undo |
| RF3 几何与手势 | 只读可见行及片段几何、坐标转换、命中、吸附和手势控制器 | 多选零点间距保持、折叠隐藏不命中、伸缩参考刷新、区域外释放、Esc/捕获丢失均有专项 |
| RF4 属性描述 | 字段描述缓存、属性路径、条件/选项、null/集合操作及两套绘制适配 | 相同编辑得到等价 JSON；混合值、创建失败、Undo/Redo 和复杂字段明确反馈 |
| RF5 扩展与预览 | 注册统一，预览资源和播放调度独立；迁移说明与重复路径整理 | 新增非 Combat 点事件/区间不用改核心分支，保存重开和双视图编辑通过；停播/异常/关闭无残留 |

每阶段先迁移一个真实入口并验证，再移其余入口；不要先创建一堆无人调用的接口。源码清理只做已证明无调用的部分，删除旧模块仍需列清单确认。全部阶段保持原版布局参照，不把重构与换皮肤、格式升级或 Combat 接入捆绑。

**RF02问题处置**：JSON选择器误列非JSON TextAsset、多选拖过零点压缩间距、null集合折叠键失效、折叠片段缓存仍参与命中、拉伸未重建磁吸参考、中键区域外释放残留平移，均已逐项复现并最小修复；另补Esc与失焦的导航取消入口。最终115/115 Editor回归通过，具体失败证据、处理器测试与完整UI链的覆盖差别、人工待验和方案编译结果均见唯一任务清单RF02执行记录。不把缺陷修复当作RF03–RF15架构迁移完成，不改变本轮未确认的正常操作习惯。

### 五、可读性与成功标准

- 命名表达业务动作和状态，不使用 mode=1/2/3 这类手势魔法数；公共 API 区分候选、提交、取消和失败。
- 方法按“输入/前置条件 → 计算候选 → 校验 → 提交 → 通知”组织，UI 回调不混入持久化和业务判断。
- 默认具体类和显式依赖，少量必要接口；文档说明不明显的所有权和边界，而不是逐行翻译代码。
- 删除死代码/重复 helper 应在对应入口迁移后进行；不以文件数、接口数或行数作为质量门槛。
- 可观察的成功标准是：加一个业务类型只补模型及可选扩展；改一条编辑规则只改一处；任一视图都能独立测试；业务无须访问静态窗口或 GUI 全局状态。

## 1. 执行摘要与项目约束

### 1.1 最终建议

采用以下主从关系：

```text
ActionEditor：通用行为时间轴编辑平台
    └─ Combat：技能及战斗事件业务扩展
         ├─ 战斗数据
         ├─ 战斗事件运行时
         ├─ 编辑器预览
         ├─ Scene 编辑工具
         └─ 示例场景
```

这条路线在两份源码现有结构上成立：ActionEditor 已有通用的资产、分组、轨道、片段和扩展机制；CombatEditor 已有战斗事件执行、角色挂点、预览和可玩示例。两者的价值可以互补。

需要完善的是 ActionEditor 的可靠性和业务扩展契约，而不是要求所有业务共用一个万能运行时。

### 1.2 本次设计前提

- 两个项目均为实验项目，没有近期生产交付要求。
- 不要求兼容旧窗口、旧 API 和旧资产格式。
- 不把兼容兜底作为目标架构。
- 编辑器现代化的主体是 ActionEditor，不是另做一套独立的 Combat 新窗口。
- Combat 已有事件运行时，接入时应优先复用其业务能力，而不是从零再造一套。
- 未来可能服务联网项目，但当前不要求立即实现预测、回滚或帧同步。

### 1.3 技术选择

**推荐原生 UI Toolkit 工作台、自定义二维时间轴控件，以及独立的 Unity Scene 工具体系。**

- 不建议用 EditorGUILayout 重新建设整个复杂工作台。
- 不以 IMGUIContainer 混合界面作为长期目标。
- Handles、EditorTool、动画采样和三维渲染预览仍使用各自适合的 API。这是职责分工，不是旧界面兼容方案。
- 不承诺 UI Toolkit 原生覆盖所有 IMGUI 或 Unity Editor 绘制能力；对本项目的二维时间轴需求，其能力足够。

### 1.4 最重要的架构原则

1. 编辑器平台与具体战斗业务分离。
2. 编辑数据、执行状态、预览状态、工作区状态分离。
3. 播放状态属于播放实例，不属于资产或 AnimationClip。
4. 时间规则显式定义，不把 Animator 进度固化为平台唯一时钟。
5. 所有资产修改通过编辑事务，绘制只读数据。
6. 网络协议不属于编辑器，但可联网执行的数据契约需要在设计中体现。

## 2. 分析范围与证据边界

### 2.1 本地项目

| 项目 | 路径 | 形态 |

## 3. 两个项目的实际定位

### 3.1 CombatEditor：动画驱动的战斗事件工具

核心结构：

```text
CombatController
    ├─ Animator
    ├─ CharacterNode 挂点映射
    └─ CombatGroup 技能分组
         └─ AbilityScriptableObject
              ├─ AnimationClip
              └─ AbilityEvent 列表
                   ├─ 时间或时间区间
                   └─ AbilityEventObj
                        ├─ 参数
                        ├─ AbilityEventEffect：运行时效果
                        └─ AbilityEventPreview：编辑器预览
```

其工作方式主要是：读取 Animator 正在播放的动画和进度，在对应时间执行附加事件。PDF 说明也明确指出，它不负责动画状态之间的切换。

已有业务包括：

- 音效、粒子、灯光、对象生成。
- 动态拖尾。
- HitBox。
- 位移和动画速度。
- 多阶段状态窗口。
- 角色节点绑定及 Scene 中的位置、旋转和碰撞盒编辑。
- 时间轴拖动、播放、循环和区间预览。
- 俯视角、2D 格斗和重攻击示例场景。

### 3.2 Combat 确实已经有自己的运行时

运行链路：

```text
角色控制器：处理输入、状态和动画切换
    → Animator：提供当前动画及 normalizedTime
    → CombatController：调度当前动画的事件
    → AbilityEventEffect：启动、持续、结束具体效果
```

主要实现包括：

| 代码 | 职责 |
|---|---|
| `CombatController.Start / InitAnimEffects` | 初始化事件实例和动画映射 |
| `RunEffects` | 读取 Animator 当前或过渡目标动画 |
| `RunningEventsOnClip` | 按动画进度驱动事件 |
| `UpdateLayerActiveClips` | 动画变化时结束旧事件 |
| `AbilityEventEffect` | 运行时事件生命周期 |
| 各种 `AbilityEventEffect_*` | 执行特效、碰撞盒、状态、位移等行为 |
| `AnimSpeedExecutor / MoveExecutor` | 动画速度和移动支持 |

所以不能把 Combat 理解为只有编辑器和预览的项目。

但它还不是包办技能条件、消耗、冷却、目标选择、完整伤害结算、Buff 和网络同步的完整战斗系统。这不妨碍其作为本次业务扩展的运行时来源。

### 3.3 ActionEditor：可扩展的通用时间轴编辑框架

核心结构：

```text
Asset
    └─ Group
         └─ Track
              └─ Clip
                   ├─ 普通片段
                   ├─ ClipSignal
                   └─ ClipCrossBlend
```

已有设计包括：

- 时间、长度、轨道和分组。
- 激活、锁定和折叠。
- 选择、多选、拖动、拉伸和吸附。
- 类型发现、分类及创建菜单。
- 自定义 Inspector 和工具栏。
- 通过 Attribute 绑定预览实现。
- FullSerializer JSON 持久化。

这些抽象适合扩展到技能、Buff、镜头和场景表现，但“框架允许实现”不等于“业务已经实现”。

### 3.4 ActionEditor 尚未提供完整的游戏执行层

`Asset`、`Group`、`Track`、`Clip` 位于 Runtime，主要提供数据和结构；`AssetPlayer`、`PreviewBase` 和 `TimePointers` 位于 Editor，主要服务编辑器预览。

因此它具备运行时可用的数据基础，但不能把现有编辑器播放器直接视为完整战斗执行器。

在目标架构中，这个缺口由 Combat 业务运行时接入，不需要 ActionEditor 平台先发展成万能战斗引擎。

## 4. 优势、局限与适用场景

| 维度 | CombatEditor | ActionEditor 2.0 |
|---|---|---|
| 主要定位 | 动画驱动的战斗事件工具 | 通用时间轴编辑框架 |
| 开箱业务 | 已有事件、预览和可玩示例 | 需要编写业务类型 |
| 数据组织 | 简单，贴近单动画事件 | 分组、轨道和片段更通用 |
| Scene 工具 | 已有挂点及碰撞盒等编辑能力 | 需业务扩展 |
| 运行时 | 已有战斗事件执行层 | 本地包未提供完整战斗执行层 |
| 时间表达 | 归一化时间，编辑器大量使用 60 帧基准 | 秒为基础，可按帧吸附 |
| 持久化 | Unity 资产和子资产 | FullSerializer JSON |
| 扩展性 | 事件可扩展，窗口耦合明显 | 扩展思想更通用，但实现有缺口 |
| 可靠性 | 需补时间、预览和执行边界 | 需补保存、输入、生命周期等基础能力 |

### 4.1 Combat 更适合

- 已有 Animator 控制器，希望给动画附加战斗事件。
- 近战、俯视角和格斗原型。
- 重视挂点、HitBox 和特效场景预览。
- 工作流以单动画及其附加事件为中心。

### 4.2 ActionEditor 更适合

- 希望多个业务共享一套时间轴编辑基础设施。
- 技能由多轨道、多片段构成。
- 项目有自己的执行系统。
- 有持续维护编辑器平台的意愿。

### 4.3 对当前目标的判断

两个项目不应继续各自维护选择、吸附、窗口布局、属性面板和拖拽逻辑。应把这些能力集中到 ActionEditor，Combat 保留和发展自己的业务能力。

## 5. 以 ActionEditor 为平台的可行性判断

### 5.1 结论：可行，并且有现成结构基础

可以建立如下业务模型：

```text
CombatAbilityAsset : Asset
    └─ CharacterGroup : Group
         ├─ AnimationTrack
         │    └─ AnimationItem
         ├─ AudioTrack
         │    └─ PlayAudioEvent
         ├─ EffectTrack
         │    └─ SpawnEffectItem
         ├─ HitBoxTrack
         │    └─ HitBoxItem
         ├─ MotionTrack
         │    └─ MotionItem
         └─ StateTrack
              └─ StateWindowItem
```

这是概念映射，不要求每一类事件单独占一种轨道，也不要求立刻支持多动画。

### 5.2 不要机械映射两个项目的 Group

Combat 的 `CombatGroup` 组织的是多个技能资产；ActionEditor 的 `Group` 组织的是一个时间轴文档内部的轨道。

正确区分：

```text
角色技能库：管理多个技能
    ├─ 普通攻击组
    │    ├─ 技能 A
    │    └─ 技能 B
    └─ 特殊技能组
         └─ 技能 C

每个技能：一个 ActionEditor 文档
    └─ 文档内 Group / Track / Item
```

技能库浏览属于资源组织；文档内部轨道属于编辑模型，不能混为一个层次。

### 5.3 迁移范围

**应保留并整理：**

- 战斗事件参数与具体效果。
- 角色节点语义和绑定。
- HitBox、位移、变速、状态窗口。
- 粒子、拖尾和对象预览经验。
- Scene 操作柄及示例。

**应由 ActionEditor 替代：**

- Combat 原时间轴窗口及其分栏。
- 通用事件列表、选择、拖拽、刻度和属性联动。
- 通用保存、复制、撤销和快捷键。

**需要针对缺陷整理，不宜原样固化：**

- 按 Clip ID 聚合执行状态。
- 全局预览数据和窗口查找。
- 通过对象名称查找预览容器。
- 散落的时间换算。
- 编辑器和运行时交叉引用。

### 5.4 判断平台化是否成功的标准

新增一种 Combat 事件，原则上只修改 Combat 扩展，不修改 ActionEditor 核心。

新增第二种非战斗业务时，原则上复用时间轴和文档能力，只增加业务定义、校验、属性和预览。

不要求第一版完美抽象，但若每次增加业务都要往核心加入类型判断，应当回头检查扩展边界。

## 6. 推荐的目标架构

### 6.1 模块划分

```text
ActionEditor.Model
    文档、轨道、时间对象、稳定标识及必要基础类型

ActionEditor.Editor
    UI Toolkit 工作台
    编辑事务、选择、撤销、属性扩展、保存和预览协调

Combat.Definitions
    技能与战斗事件定义

Combat.Runtime
    播放实例、时间驱动、调度、执行器和角色上下文

Combat.Editor
    事件注册、属性面板、校验、预览与 Scene 工具

Combat.Samples
    示例角色、资产和测试场景
```

以上是建议职责，不要求第一天就创建所有程序集；可以在规模较小时合并部分模块，但保持依赖方向。

### 6.2 依赖规则

- ActionEditor 核心不能反向依赖 Combat。
- Combat.Editor 可以依赖 ActionEditor.Editor 和 Combat.Runtime。
- Combat.Runtime 不能依赖任何 Editor 程序集。
- 如果战斗数据直接基于 ActionEditor 的模型，Combat 可以依赖无 Editor 引用的数据基础层。
- 若未来使用非 Unity 服务器，应使导出的权威逻辑数据和执行层不依赖 Unity 对象；不要求整个编辑模型立即脱离 Unity。

### 6.3 四类状态必须分离

| 状态 | 示例 | 生命周期 |
|---|---|---|
| 编辑资产 | 技能时长、事件时间、参数、资源引用 | 持久化 |
| 工作区状态 | 缩放、滚动、折叠、面板宽度 | 用户或文档工作区 |
| 执行状态 | 当前 Tick、已触发事件、取消标志 | 一次技能播放 |
| 预览状态 | 临时对象、采样缓存、角色副本 | 一次预览会话 |

当前 ActionEditor 资产中的视图时间范围等字段，适合移到工作区状态。用户调整界面不应改变技能运行定义。

### 6.4 不构建万能播放器

平台可以提供时间转换、事件遍历等可复用算法，但业务执行语义由业务定义。

- 技能可能按固定 Tick 推进。
- 镜头序列可能按连续时间求值。
- Buff 可能由服务器状态和剩余时长驱动。

共享编辑能力，不意味着强制共享所有执行机制。

## 7. 数据模型、时间规则与扩展契约

### 7.1 时间对象的基本语义

建议显式区分：

1. **点事件**：音效、生成、发射和通知等瞬时动作。
2. **区间片段**：攻击判定、动画、位移、状态和镜头效果。
3. **阶段或窗口集合**：前摇、生效、后摇、连招和取消窗口。

底层可以共享字段，但不能仅用“普通片段长度为零”替代点事件触发规则。

### 7.2 时间表示的建议

> A02 已定案：平台保存有限非负 double 秒，帧率/Tick 为显式业务映射；边界、排序、循环、身份、分类及扩展冲突规则见 [ActionEditor 时间与扩展契约](ActionEditor-Contracts.md)。以下保留设计背景，不再视为未决定的格式选项。

平台不应在代码各处混用秒、归一化时间、固定 60 帧和动画采样帧率。

对 Combat 技能逻辑，优先评估：

- 显式配置逻辑帧率或模拟 Tick。
- 使用整数逻辑时间表示关键事件。
- 动画、界面和连续曲线通过统一转换服务求值。
- 动画源采样帧率与技能逻辑帧率可以不同。

对镜头和自由演出，可以采用连续时间，但必须定义与平台公共时间坐标的转换。

最终存储形式仍需在原型中决定；本建议并非要求所有业务强制使用同一帧率。

### 7.3 必须明确的规则

- 区间是左闭右开还是其他约定。建议优先考虑 `[start, end)`，并为点事件单独定义跨越规则。
- 事件恰好位于 0 和结束时间时如何处理。
- 一次推进跨越多个事件时是否全部触发。
- 同一时刻多个事件的稳定执行顺序。
- 循环边界和跨多个循环的处理。
- 中断、取消、停止和正常结束的区别。
- 时间缩放作用于哪些时钟。
- 跳转、倒拖与游戏运行推进的区别。

规则必须由测试保证，不能依赖绘制顺序或容器碰巧有序。

### 7.4 明确业务扩展注册

每种业务类型按需提供：

| 扩展 | 职责 |
|---|---|
| 定义 | 类型、参数和时间语义 |
| 默认值工厂 | 新建时初始化 |
| 时间轴视图 | 片段、点事件和摘要表现 |
| 属性编辑器 | 参数编辑 |
| 校验器 | 业务与时间合法性 |
| 预览实现 | 编辑器求值 |
| 执行或导出实现 | 游戏执行、数据构建 |

这些职责不必由同一个类承担。保留 Attribute 发现机制是可行的，但应有清楚的注册和冲突规则。

### 7.5 重叠和混合由业务策略决定

不能由一种通用相邻片段算法决定所有轨道行为。

| 轨道 | 可能的策略 |
|---|---|
| 动画 | 允许受约束的交叉混合 |
| 音效 | 允许重叠 |
| HitBox | 允许多个独立判定，或由业务限制 |
| 状态窗口 | 可重叠、互斥或按优先级处理 |
| 位移 | 累加、覆盖、混合或禁止重叠 |

策略可以挂在轨道或业务描述上，编辑命令和运行时应使用一致的约束定义。

### 7.6 编辑事务

所有资产修改通过统一入口，例如：

```text
AddItem
DeleteItems
MoveItems
ResizeItem
DuplicateItems
ChangeProperty
```

拖动事务：

```text
按下记录初态
    → 拖动中展示候选状态
    → 松开校验并提交
    → Esc 或捕获丢失时取消或按明确规则结束
```

一次拖动对应一个撤销事务。新增和删除子对象也必须处于同一事务边界。

### 7.7 持久化和运行数据构建

#### A01 已定案（2026-11-09）

正式编辑格式采用单个 Unity `ScriptableObject` `.asset` 根对象，内部 Group/Track/Event 为普通可序列化值对象，多态事件通过 `[SerializeReference]` 存储；事件参数直接持有持久 Unity 资源引用。第一版不把每个事件拆为独立子资产，不让事件跨文档共享可变实例。

- 根对象拥有完整定义、格式版本、稳定文档 ID；Group/Track/Event 各自具有稳定 ID。复制生成新 ID，不以资源实例 ID 作为持久身份。ID 与时间的具体契约由 A02 落定。
- 文档会话持有工作副本，工作区和播放/预览状态不写入定义。所有业务修改经命令事务，对根对象记录完整 Undo，子对象随同一根对象恢复。
- 保存服务负责合法性、未知多态类型/失效引用诊断、失败传播和可靠提交；不能仅凭 `SaveAssetIfDirty` 就声称文件提交可靠。具体实现与故障回归属于 A03/A05。
- Unity `SerializedObject` 只能用于 ScriptableObject 根及其序列化字段，不直接包装任意普通对象。属性修改仍经事务，不能绕过校验。
- JSON 不再作为第二套正式编辑存储。FullSerializer 原始路径保留参照，危险入口在 A03 隔离；不要求旧格式迁移，但原始数据不删除或覆盖。

选择依据：A01 经用户确认后，通过固定范围 CLI 探针实际完成两种多态事件、时间/参数/Unity 资源引用、Undo/Redo、保存、卸载及重新加载，并清理隔离样本。原有 JSON 基线能往返时间和基本参数，但根是普通对象，现有实现没有 Unity 资源引用映射、可靠提交或 Undo 所有权；继续使用需自建这些机制。单根 SerializeReference 方案以较少资源生命周期操作覆盖当前需求，不选多子资产方案作为首版。

本结论只证明编辑格式技术路径可用，不代表新平台模型、正式存储、未知类型安全或 UI 已实现。实际证据及未覆盖范围见任务清单 A01 记录。

建议保留明确的数据构建出口：

```text
编辑资产
    → 校验
    → 排序、时间转换、资源解析
    → 可执行定义或导出数据
```

它可以在加载时或构建时执行，初期不需要复杂编译器。

编辑资产可优先评估 ScriptableObject 配合子资产或 SerializeReference，以便利用 Unity 原生引用、属性和撤销；这不是联网运行格式的要求。若继续采用 JSON 普通对象图，则需要显式属性绑定、命令和可靠存储，不应假设 SerializedObject 可直接包装任意普通 C# 对象。

运行数据不应包含窗口、反射 Inspector、视图范围和临时预览状态。

## 8. Combat 运行时的复用与演进

### 8.1 第一阶段应优先复用

- 保留 Animator 驱动的本地使用场景。
- 保留事件启动、持续和结束的业务生命周期。
- 尽量复用粒子、音效、HitBox、状态和位移效果实现。
- 调整数据读取，使 ActionEditor 编辑结果能被 Combat 运行时消费。
- 以现有示例作为行为参照。

不必先做全新的通用技能播放器，再接入最小业务。

### 8.2 应逐步调整的执行状态模型

当前按 AnimationClip ID 查找事件的方式不足以代表具体技能身份。

推荐模型：

```text
CombatPlaybackInstance
    ├─ 技能定义
    ├─ 角色与执行上下文
    ├─ 时间来源
    ├─ 当前时间、循环和取消状态
    └─ 每个事件的独立执行状态
```

可以解决或为解决以下问题提供基础：

- 同一动画对应不同技能。
- 同一技能被多个角色同时使用。
- 多 Animator Layer。
- 重复释放、中断和取消。
- 未来网络实例身份和重演。

实例化模型本身不会自动解决所有过渡、判定或同步问题，仍需具体策略。

### 8.3 时间轴与状态机分工

时间轴负责技能内部时间结构；状态机或 Ability 系统负责技能之间的选择与切换。

例如：时间轴声明第 20～30 帧允许连招，状态机结合输入、资源和当前状态决定是否切换。

不建议一开始同时开发大型节点图系统。先提供清楚的窗口查询、技能请求和中断接口即可。

## 9. 预览系统与场景编辑

### 9.1 预览不是直接执行真实战斗

游戏执行主要考虑向前推进和真实副作用；编辑器还需要任意跳转、向后拖动、参数变化后重建以及资源清理。

应共享业务定义、时间转换和适当的计算代码，不应直接共享带真实伤害、扣资源等副作用的完整执行链路。

### 9.2 预览会话

```text
PreviewSession
    创建
    → 绑定预览角色
    → 建立预览对象与缓存
    → 求值到指定时间
    → 修改后刷新或重建
    → 恢复并释放
```

预览上下文按需提供：

- Animator 或动画求值服务。
- 挂点映射。
- 临时对象所有权。
- 时间和采样方式。
- 场景编辑工具。
- 清理及恢复服务。

不要由每个事件全局查找窗口、角色或命名对象。

### 9.3 求值顺序

Combat 存在明确依赖：

```text
动画姿势
    → 角色根运动和挂点
    → 特效、碰撞盒与其他附属对象
    → Scene 辅助显示
```

不跟随角色的特效还可能需要查询生成时刻的姿势。平台应支持明确采样阶段或业务提供的求值服务，而不是只依赖对象列表遍历顺序。

### 9.4 生命周期

至少覆盖：

- 切换资产和角色。
- 新增、删除和修改事件。
- 关闭窗口。
- 切换场景。
- 脚本重编译。
- 进入和退出 Play Mode。
- 异常发生后的清理。

是否采用隔离预览场景、角色副本或直接预览场景角色，需要根据 Scene 编辑需求实测决定。使用副本有利于隔离，但不能不加判断地实例化并运行全部角色脚本。

## 10. UI Toolkit 技术选择与能力边界

### 10.1 结论

在当前 Unity 2022.3 下，推荐 UI Toolkit 作为新 ActionEditor 工作台主体，不需要仅为这项改造同时升级 Unity 主版本。

EditorGUILayout 和 GUILayout 属于 IMGUI。两个旧编辑器已经大量使用该体系；把手写 Rect 改成 EditorGUILayout，不等于完成现代化。

### 10.2 复杂布局支持

UI Toolkit 支持 Flexbox 子集、嵌套容器、滚动、列表、树、绝对定位和覆盖元素。TwoPaneSplitView 支持横向、纵向以及可拖动分隔，要求恰好两个直接子元素，可以嵌套组合。

建议初期工作台：

```text
┌─────────────────────────────────────────────────────┐
│ 文档 / 工具栏 / 播放控制 / 校验状态                    │
├────────────┬───────────────────────────┬────────────┤
│ 资源与技能树 │ 时间轴 / 动画预览          │ 属性面板    │
│ 搜索和过滤   ├───────────────────────────┤            │
│             │ 问题列表 / 事件日志        │            │
└────────────┴───────────────────────────┴────────────┘
```

自定义任意面板停靠、可拖拽页签和布局序列化不是一个现成控件即可完成。初期应优先使用固定区域加可调整分栏，而非自研 IDE 窗口系统。多个 EditorWindow 可以使用 Unity 自身的窗口停靠，不应依赖内部未公开的停靠 API 建立核心功能。

### 10.3 复杂绘制支持

| 需求 | 推荐方案 | 能力判断 |
|---|---|---|
| 工具栏、搜索、属性面板 | 标准 UI Toolkit 控件 | 适合 |
| 时间刻度、片段、区间、播放头 | 自定义 VisualElement | 能实现 |
| 辅助线、形状和曲线 | generateVisualContent / Painter2D / Mesh API | 能实现 |
| 框选、缩放、平移和拖拽 | Pointer 事件、Manipulator、指针捕获 | 能实现 |
| 曲线控制点和波形编辑 | 自定义绘制及命中检测 | 需要开发交互 |
| 三维碰撞盒和挂点操作 | Handles / EditorTool | 应使用 Scene 工具体系 |
| 三维角色预览 | 独立渲染服务并显示结果 | 不由二维控件独自解决 |
| 任意旧 IMGUI 控件 | 原生重设计 | 不存在逐项等价保证 |
| 任意自定义材质、GL 路径 | 单独评估渲染方案 | 2022.3 UI Toolkit 不是直接替代品 |

可以完成本项目的二维编辑，不等于原生覆盖 Unity Editor 的一切绘制能力。

官方支持 IMGUIContainer，但在当前不要求兼容的前提下，不将其作为目标架构。

### 10.4 时间轴实现建议

```text
TimelineCanvas
    ├─ 背景与刻度
    ├─ 可见轨道和片段
    ├─ 选中与拖拽反馈
    └─ 播放头及提示覆盖层
```

- 不给每条刻度线创建独立 VisualElement。
- 不在每次播放更新时重建整个视觉树。
- 绘制、命中检测、坐标转换与编辑命令分离。
- 长列表采用虚拟化或可见区域复用。
- 原生 UI Toolkit 属性面板不依赖旧反射 Inspector 布局。
- 处理 PointerCaptureOut、焦点丢失和面板分离。
- 播放更新与资产修改触发不同范围的刷新。

UI Toolkit 不天然保证比 IMGUI 更快，仍需测量布局、网格生成、分配和重绘成本。

### 10.5 Unity Timeline 的位置

Unity Timeline 更适合多角色演出、镜头、音频和 Director 驱动编排。它可以成为后续业务集成对象，但不建议为省 UI 而把当前战斗系统全面改成 Director 主导。

战斗技能的取消、判定和联网语义仍需业务实现；Timeline 窗口也不是可任意嵌入的通用控件。

## 11. 联网项目支持与职责划分

### 11.1 可以支持，但不是已有联网能力

同一编辑器可以制作单机、服务器权威、预测或回滚架构使用的技能。前提是数据契约和运行时语义明确。

当前 Combat 运行时不能仅因接入 ActionEditor 就被认定为支持联网。

### 11.2 职责划分

| 编辑器与数据构建层 | 联网运行时 |
|---|---|
| 稳定技能与事件 ID | 技能请求及权限检查 |
| 明确时间单位与边界 | 权威起始 Tick |
| 同时间事件稳定排序 | 服务器接受或拒绝 |
| 逻辑与表现分类 | 预测、纠正与回滚 |
| 资源稳定标识 | 命中与伤害权威 |
| 版本与内容校验信息 | 状态和中断同步 |
| 执行模式合法性校验 | 表现去重与取消 |
| 运行数据导出 | 网络协议和版本匹配 |

编辑器通常不负责网络发包，但不能完全忽略网络执行需要的数据条件。

### 11.3 时间驱动方向

当前 Combat 主要是：

```text
Animator 进度 → 战斗事件
```

联网权威逻辑通常更适合：

```text
权威技能时间 / 模拟 Tick
    ├─ 逻辑事件
    └─ 动画与表现对齐
```

Animator 的混合、速度、求值和裁剪等情况不应单独决定权威伤害时机。

不要求所有动画都由技能系统完全接管，但应允许与动画表现独立的逻辑时钟。

### 11.4 逻辑与表现分类

| 事件 | 类型 | 常见位置 |
|---|---|---|
| 资源消耗 | 逻辑 | 权威端，预测视架构而定 |
| 攻击判定窗口 | 逻辑 | 权威模拟 |
| 伤害结算 | 逻辑 | 权威模拟 |
| 逻辑弹丸 | 逻辑 | 权威模拟 |
| 刀光粒子、音效 | 表现 | 客户端 |
| 摄像机震动 | 表现 | 相关客户端 |
| 命中反馈 | 表现 | 由预测或确认结果驱动 |

可以在同一时间轴编辑，不必做两套编辑器。分类应服务校验、导出和执行，而不是只改变颜色。

HitBox 的几何参数可以共享，但本地 Collider、服务器判定描述和编辑器可视化不必共用同一段执行代码。

### 11.5 固定 Tick 不等于确定性

整数时间并不能自动消除以下不确定性：

- 普通浮点计算。
- Unity 物理。
- 无序集合遍历。
- 随机数。
- Animator 求值。
- 外部状态和执行顺序。

严格帧同步或回滚需要额外约束和验证，不能只增加一个“联网模式”开关。

### 11.6 重演与副作用

逻辑可能因回滚重复执行，音效与粒子不应因此无条件重复生成。

可使用如下身份概念：

```text
技能实例 ID + 事件 ID + 循环或触发序号
```

编辑器负责稳定事件 ID，运行时负责副作用去重、撤销或延迟确认策略。

### 11.7 现在与未来的投入边界

**现在值得做：**

- 分离数据、状态和编辑器。
- 稳定标识，避免 GetInstanceID 充当持久身份。
- 明确时间、顺序、逻辑与表现。
- 播放实例与执行上下文。
- 校验和数据构建出口。

**有明确联网项目后再做：**

- 选择服务器权威、预测或帧同步方案。
- 快照、回滚和网络协议。
- 实际服务器判定。
- 网络条件下的重演和表现去重。
- 对应调试与校验面板。

一般联网动作项目可优先评估服务器权威；竞技格斗等严格回滚需求应单独设计，不沿用同一组假设。

- 保存等数据安全问题优先处理，避免继续试用时损坏资产。
- 不以重写为理由忽略已有的业务行为和示例参照。

## 13. 实施路线与阶段验收

以下是阶段级设计路线，不是逐项执行记录。具体任务、依赖、交付物、验收条件和项目重命名后的恢复步骤见 [执行任务清单](../.codex/tasks/action-editor-refactor.md)。后续按用户指定的任务编号推进，不自动执行整个阶段。

### 阶段 A：基础整理与边界确定

目标：确定 ActionEditor 平台职责、Combat 业务职责和程序集依赖。

工作：

- 决定编辑资产形式。
- 定义时间和事件身份规则。
- 整理运行时与 Editor 引用。
- 建立保存安全和关键缺陷回归用例。

验收：基础程序集能够编译，数据保存失败不会破坏原文件，依赖方向明确。

### 阶段 B：ActionEditor 原生 UI Toolkit 最小工作台

工作：

- 主窗口、分栏、资源列表、属性面板。
- 文档上下文，替代静态全局状态。
- 基础点事件和区间对象。
- 时间轴绘制和坐标转换。
- 编辑事务、Undo/Redo、保存及重开。

验收：新增、移动、缩放、删除、取消和撤销均有一致行为，绘制不修改资产。

### 阶段 C：最小 Combat 用例闭环

选择一个已有攻击动作，接入：

- 一个动画。
- 一个音效点事件。
- 一个挂点特效。
- 一个 HitBox 区间。
- 一个连招窗口。

验收链路：

```text
创建 → 编辑 → 撤销 → 保存 → 重开 → 预览 → 运行 → 中断清理
```

本阶段优先复用现有 Combat 执行能力，不要求同时完成完整联网运行时。

### 阶段 D：复杂 Combat 与时间语义

工作：

- 位移、变速、拖尾。
- 不跟随挂点的特效。
- 多阶段窗口。
- 循环和跨帧触发。
- 播放实例隔离。
- 过渡、中断和多层策略。

验收：同动画不同技能、重复播放和独立角色不会串状态；预览跳转与连续播放满足已定义语义。

### 阶段 E：第二业务验证

加入 Buff 表现或简单镜头序列之一。

验收：主要通过业务注册、属性、校验和预览扩展完成，不需要重写时间轴或把业务判断散入核心。

### 阶段 F：面向实际联网项目增强

有明确需求后，再接入权威时钟、服务器数据、预测和回滚等能力。

验收应围绕实际网络架构，不以“支持固定帧”作为联网完成标准。

## 14. 测试与性能验证

### 14.1 功能验证矩阵

| 领域 | 必测场景 |
|---|---|
| 保存 | 损坏 JSON、序列化失败、只读文件、切换失败、自动保存 60/120 秒 |
| 编辑事务 | 新增、删除、拖动、缩放、重排、批量修改、取消、Undo/Redo |
| 输入 | 拖出区域、捕获丢失、失焦、右键、滚动后的命中、不同缩放 |
| 资产 | 模板复制保留全部时间和参数，资源引用重开一致 |
| 时间 | 0、结束点、相同时间、短事件、跨多个事件、跨循环 |
| 预览 | 切换 A/B、增删后重播、倒拖、随机跳转、修改后求值 |
| 生命周期 | 关闭窗口、切场景、编译、进出 Play Mode、异常清理 |
| 战斗运行 | 同动画复用、多角色、多层、过渡、中断、重复释放 |
| 发布 | 实际 Player Build，而不只是 Editor 编译 |
| 联网增强 | 重复事件、延迟确认、回滚重演、数据版本不一致 |

### 14.2 独立参照

- 使用现有示例与原始配置作为行为参照，同时识别其中已有缺陷。
- 为时间边界写明确预期，不用新实现自身输出定义正确答案。
- 导出后重新加载，比较业务定义而不是只检查文件存在。
- 连续播放和跳转求值分别测试，不能假设两者一致。

### 14.3 性能验证

目前没有真实性能基线，不设置未经验证的毫秒或数量保证。

后续应在实际最重文档与首开路径测量：

- 打开文档与首次预览耗时。
- 滚动、缩放、拖动和持续播放的帧耗时。
- GC 分配和布局、绘制成本。
- 大量轨道及事件时的可见区域裁剪效果。
- 连续新增删除、刷新和重开窗口后的对象及内存增长。
- 多次创建销毁 PreviewSession 后的资源残留。

先测量再优化，不以改用 UI Toolkit 作为性能通过的证据。

## 15. 需要避免的设计误区

1. **把 Combat 整个旧窗口嵌入 ActionEditor。**目标应是原生业务接入。
2. **把 ActionEditor 当作现成完整战斗运行时。**它主要提供编辑与数据基础。
3. **认为 Combat 没有运行时。**它已有事件执行层，应复用和整理。
4. **先完整修好所有旧 UI，再重写一遍。**替换模块应通过新实现和回归测试解决。
5. **把技能库分组与文档内部 Group 混为一谈。**两者层次不同。
6. **所有事件都使用同一重叠规则。**时间合法性需要业务策略。
7. **让 Animator 成为平台唯一时钟。**不利于独立模拟和联网权威。
8. **把整数帧视为确定性保证。**物理、随机和求值仍需约束。
9. **在预览中执行真实伤害或资源消耗。**应隔离副作用。
10. **在绘制中直接修改资产。**会引出量化、撤销和保存问题。
11. **为“纯 UI Toolkit”重造三维 Handles。**应按职责选择 API。
12. **第一阶段就建设万能框架、节点图、任意停靠和完整网络栈。**先打通真实业务闭环。

## 16. 最终结论与待决策事项

### 16.1 最终结论

**以 ActionEditor 为主项目，将 CombatEditor 作为其业务用例，是可行且值得实施的方向。**

ActionEditor 的通用模型和扩展思想可以保留并完善；有缺陷的输入、View、存储和全局状态模块可以在现代化过程中替换。Combat 的运行时、预览、挂点、碰撞盒及示例是现成业务资产，不应被忽略。

目标不是两套窗口共存，也不是从零重做完整战斗引擎，而是：

> 一套原生 UI Toolkit 行为时间轴编辑平台，加上拥有自身数据、执行和预览的 Combat 业务模块。

未来联网通过明确时间、稳定身份、逻辑与表现分类以及独立执行上下文接入。网络同步不属于编辑器核心，但编辑器必须能产出适合对应执行模式的数据。

### 16.2 已明确的方向

- ActionEditor 为通用编辑平台。
- Combat 为第一套完整业务扩展。
- 不承担旧界面和旧格式兼容要求。
- UI Toolkit 为新界面主体。
- Scene 工具与渲染预览独立。
- 优先真实技能闭环，再验证第二业务。

### 16.3 实施前仍需决策

| 决策 | 建议起点 |
|---|---|
| 编辑资产格式 | A01 已定案：单根 ScriptableObject + SerializeReference；正式可靠存储仍由 A03/A05 验收 |
| Combat 权威时间 | 优先评估显式逻辑帧或 Tick，保留动画时间映射 |
| 第一版动画模型 | 先一个技能一个主要动画，再按用例扩展 |
| 预览对象隔离 | 优先验证隔离实例与 Scene 编辑需求能否兼顾 |
| 阶段窗口表达 | 根据连招和取消查询需求决定独立区间或阶段集合 |
| 第二业务 | Buff 表现或简单镜头序列，选一个验证通用性 |
| 网络架构 | 实际项目明确后决定，不在编辑器阶段预先承诺全部模式 |

这些事项不影响总体方向，但在编码前应形成具体、可测试的实现决策。
